# Kata test hosts

Real VMs — real guest kernel, real systemd — on the local machine, in
about six seconds each. This is the local alternative to provisioning
Atlantic.net pairs for a benchmark round, and it does things no container
can.

## Why, precisely

Podman already gives real systemd: `podman run --systemd=always` with
`/sbin/init` boots systemd as PID 1, and `systemctl` enable/disable/start/
stop/restart and a full `list-unit-files` all behave. The `service:` and
`service_facts:` work in 0.9.727-0.9.728 was verified that way. **If
systemd is all you need, podman is simpler — use it.**

What podman cannot do is anything that needs a real *kernel*, because the
container shares the host's:

- `sysctl -w` / the `sysctl:` module — `/proc/sys` is read-only in a
  container. This is the whole `dev-sec.os_hardening` /
  `konstruktoid.hardening` class, which is why those roles' kernel and
  sysctl tasks have gone unverified.
- `modprobe` and module state.
- netfilter/nftables beyond what `--cap-add=NET_ADMIN` exposes.
- filesystem modules, reboot semantics, cgroup manipulation.

Verified live here: `sysctl -w net.ipv4.conf.all.rp_filter=1` and
`kernel.randomize_va_space=2` both apply for real, and the guest reports
kernel `6.18.35` where the host runs `6.12.105` — genuinely a different
kernel, not a namespace trick.

## Prerequisites

Already set up on this machine:

- Kata 4.1.0 at `/opt/kata`, containerd running with `kata-clh`
  (cloud-hypervisor) as its default CRI runtime.
- `/dev/kvm` reachable by the user via ACL.
- The user in the `containerd` group. **If a shell predates that
  membership**, `id` won't show it and `ctr` gets "permission denied" on
  the socket — `sg containerd -c '...'` works around it without a
  re-login. The scripts here use `sudo -n ctr` instead, which sidesteps
  it entirely.
- A NOPASSWD sudoers entry covering `ctr`, `ip`, `kill` (and others).
  Everything here depends on it. Check with `sudo -ln` — and read the
  whole output, not the first few lines: the Defaults block comes first
  and the actual entries come after it.
- A host-side NAT rule so guests reach the real internet, not just each
  other's `/24`: `sudo iptables -t nat -A POSTROUTING -s 10.99.0.0/16 -o
  <host-default-iface> -j MASQUERADE`, plus `net.ipv4.ip_forward=1`
  (already the default on most desktop kernels — check
  `/proc/sys/net/ipv4/ip_forward`). Without this a guest gets an address
  and a working default route (net_up adds that) but every off-subnet
  packet is dropped at the host: DNS resolution fails, `apt-get update`
  can't reach a real mirror, `curl`/GitHub-API-style tasks fail outright.
  `iptables` is deliberately NOT in the NOPASSWD list above (it's a
  wider, host-network-affecting change) - run this once by hand.

## Use

```bash
./build.sh                      # build the image + import into containerd
./kata-host.sh up   kkri 1      # -> 10.99.1.2, ssh-ready
./kata-host.sh up   kans 2      # -> 10.99.2.2
./kata-host.sh down kkri
```

Each host gets `10.99.<octet>.2`, reachable directly from the host over a
veth pair — no port forwarding. `key`/`key.pub` are generated by
`build.sh` and gitignored. An inventory line is just:

```
target ansible_host=10.99.1.2 ansible_user=root ansible_ssh_private_key_file=<path>/key
```

A pair (one host per engine) is the same shape as the Atlantic.net
workflow in the repo's `CLAUDE.md`, so a round can run locally.

## Gotchas, all of them hit for real

Everything below cost a debugging cycle. The script encodes each fix; this
is the record of *why*, so nobody re-derives it.

1. **`--privileged` alone fails.** It tries to pass every host device into
   the VM and dies with `get host path failed / No such file or directory`.
   It must be paired with `--privileged-without-host-devices`. Without
   privileged at all, `/proc/sys` stays read-only and `sysctl -w` gets
   "permission denied" — which defeats the entire point of using Kata.

2. **systemd exits instantly and silently without `--env
   container=docker`.** No output, no error, task just goes `STOPPED`.
   That env var is how systemd knows to take its containerized boot path.
   Also needs tmpfs on `/run` and `/run/lock` — the rest of what podman's
   `--systemd` does for you.

3. **A netns is single-use.** Kata leaves a `tap0_kata` device and a tc
   ingress filter behind. Reusing the netns fails with either
   `unsupported link type: tuntap` or `add virt ingress ... File exists`.
   Delete and recreate the netns for every run.

4. **Never recreate the netns under a live VM.** The shim talks to the
   kata agent over that network; cut it and `ctr task kill` hangs forever
   rather than failing — it will sit there past any timeout you give the
   surrounding command. Recovery is killing the `containerd-shim-kata-v2`
   process and its children (the VMM and virtiofsd) directly, which is why
   `kill` is in the sudoers list. `force_down` does this in the right
   order.

5. **`ctr` has no `--tmpfs`**; it's `--mount type=tmpfs,src=tmpfs,dst=...,
   options=rw:nosuid:nodev:mode=755`. And `ctr run -t` needs a real
   console — it panics with `provided file is not a console` when stdout
   isn't a tty, so it's useless from a script. `--log-uri file:///...`
   also failed here (`open stdout: No such file or directory`); to see
   why a guest died, check `journalctl` for the `kata` unit instead.

6. **Removing a container is three steps**, and a half-removed one blocks
   the next run with `snapshot "<name>": already exists`: `ctr task rm -f`,
   `ctr container rm`, `ctr snapshot rm`.

7. **Debian trixie, not Alpine.** krikri's plugin binaries are glibc-linked
   and are uploaded to the target; a musl guest cannot execute them at all
   and the upload fails before any module runs.

8. **A route added to the netns after the guest has already booted is
   invisible to the guest.** kata-agent reads the netns's network state
   once, at sandbox start, and clones it into the guest - `net_up` must
   add the default route (`ip -n $ns route add default via <gw>`)
   *before* `up()` calls `ctr run`, not after. Missed this on the first
   pass and burned most of a 120-role test round on it: guests had an
   address but no route out, so every role needing real internet (apt
   beyond the image's build-time-snapshotted cache, `curl`, GitHub API
   calls) failed identically on both engines but at different points in
   each engine's own bootstrap order - which *looked* exactly like a pile
   of real engine divergences until traced back to the network gap.
   Needs the host-side NAT rule above too, or the route just leads
   nowhere.

## Verified

A `sysctl:` differential across a Kata pair — real `ansible-playbook` on
one host, `krikri-playbook` on the other — matched exactly: `ok=7
changed=2` on both, identical `ansible_kernel` (6.18.35) and
`ansible_service_mgr` (systemd) facts, `rp_filter` genuinely 1 in the
kernel afterwards on both, and the repeat task correctly a no-op.
